# 4. Роли и права доступа

## Модель ролей

| Роль | Код | Описание |
|------|-----|----------|
| Студент | `student` | Основной пользователь. Полный доступ к бронированию, рейтингу, наградам, командам, материалам, анкете ДКШ |
| Школьник / гость | `guest` | Ограниченный доступ. Только просмотр расписания, направлений, новостей, карты |
| Тренер / организатор | `trainer` | Подтверждение посещений, управление своими слотами, просмотр списка участников |
| Администратор | `admin` | Полный доступ ко всем функциям управления платформой |

## Матрица прав доступа

### Публичные страницы (без авторизации)
- Главная страница
- Страница входа / регистрации
- Каталог направлений (только просмотр)

## Реализация в коде

Роль хранится в поле `role` таблицы `users` как enum: `student | guest | trainer | admin`.

Проверка прав реализуется через middleware/guard на бэкенде и route guard на фронтенде.

Каждый API-эндпоинт декорирован списком допустимых ролей:
```
@roles('admin')
@roles('student', 'trainer', 'admin')
@roles('*')  // все авторизованные
@public()    // без авторизации
```

## Расширяемость

Архитектура готова к добавлению:
- Новых ролей (например, `moderator`, `partner`)
- Гранулярных permissions (через промежуточную таблицу `role_permissions`)
- Иерархии ролей (через поле `parent_role`)

На старте эти механизмы не реализуются, но структура данных позволяет добавить их без миграции схемы.
